# Reflex Next 后端生产化路线图

更新时间：2026-07-14
当前基线：`v0.7.0-alpha.7` 开发中
目标版本：`v1.0.0`

## 1. 长期目标

将 Reflex Next 后端从“核心功能和离线契约完整”推进到“可以正式上线、公开推广、长期维护”的生产级桌面运行时。

成熟状态必须同时满足：

- 用户可稳定完成文本优化、取消、重试、翻译、批处理、历史和模型管理；
- 密钥、正文、历史和插件权限有清晰且经过验证的安全边界；
- Provider 变化、上游故障、Sidecar 崩溃和本地数据异常不会让产品失控；
- 冷启动、内存、并发、取消和长期运行达到量化预算；
- 从源码验证、构建、安装、升级、回滚到发布均可复现；
- 生产问题有脱敏诊断证据，不依赖用户理解技术堆栈；
- 每个正式版本都有来源、校验、变更、风险和恢复说明。

## 2. 当前判断

当前项目处于“Working / Growing”阶段：阶段 0 生产基线已关闭，Provider/Runtime 资源治理、主要本地数据安全边界、构建物料、本地轮转诊断、诊断包安全导出、插件/历史三轮资源基线以及语义模型生命周期互斥已完成，统一 Windows CI、敏感扫描和依赖审计已经形成门禁。当前工作集中在真实 Provider 证据、72 小时长期运行、历史大数据量性能和发布生命周期。

当前最大阻塞点：

1. 真实 Provider 流式与取消仍缺使用新凭据和重建候选 Sidecar 的最终实机证据；
2. 72 小时持续浸泡尚未执行，10,000 次本机门禁与三轮 1,000 次插件/历史资源基线已通过；
3. 安装、升级、卸载、重装、签名和回滚尚未完成正式生命周期验证。

## 3. 范围与非目标

### 3.1 本路线图包含

- `packages/reflex-core` 的稳定契约和性能预算；
- `packages/reflex-runtime` 的协议、插件发现、并发和进程生命周期；
- Provider、历史、翻译、批处理、Markdown 和语义模型插件；
- Tauri/Rust Host 的命令权限、配置、密钥、窗口和 Sidecar 管理；
- 测试、CI、依赖审计、构建、安装、升级、回滚和发布证据；
- 本地脱敏诊断、性能基准、浸泡测试和维护制度。

### 3.2 `v1.0` 前明确不做

- 不重写 Python Core 或改回 PyQt 架构；
- 不建设云端账号、云同步、服务端数据库或强制遥测；
- 不默认加载语义大模型；
- 不开放第三方插件市场和不受信任插件安装；
- 不在前端或配置文件保存明文 API Key；
- 不为追求指标而引入重型监控平台；
- 不同时扩展大量新 Provider，先保证现有 Provider 契约稳定。

## 4. 生产级质量门禁

### 4.1 功能与兼容

- Core、Runtime、Rust Host 和插件自动测试全部通过；
- Runtime 协议保持版本化，旧前端在兼容窗口内不会静默失效；
- Provider、模型和插件目录由后端可信元数据产生，前端不重复维护真值；
- 所有取消、超时、重试、空响应和崩溃恢复均有确定性测试；
- Release 构建不得设置开发模式，`provider=mock` 在生产运行时必须被拒绝；
- Runtime 默认最多 4 个活动优化任务、32 个等待任务，超限返回稳定忙碌错误；
- 单请求默认总时限 120 秒，输出上限 2 MiB，分片上限 50,000；
- 场景识别失败继续回退 `general`，不阻塞优化。

### 4.2 安全

- 发布前 P0/P1 安全问题为 0；P2 必须有修复计划和明确接受人；
- 密钥只存在于 Windows Credential Manager 和受控进程内存；
- 日志、事件、错误、历史、导出、截图和安装包不含密钥或完整敏感输入；
- Tauri capability、Runtime 私有命令和插件操作采用最小权限白名单；
- TLS 校验不可关闭，自定义 CA 路径有边界校验；
- Markdown、CSV、路径、JSON、SQLite 和进程输入有负向安全测试；
- Python、Rust、npm 依赖在发布前完成已知漏洞审计和许可证检查。

### 4.3 可靠性

- 72 小时、至少 10,000 次无网络 Mock 请求与取消循环无死锁、无丢失终态、无请求串线；
- 1,000 次混合插件调用后，进程私有内存增量不超过稳定基线的 20% 或 50 MB，取更严格者；
- Sidecar 异常退出后，下一次请求在 3 秒内恢复到可执行或明确错误；
- 本地取消确认 P95 小于 250 ms，取消后 500 ms 内不得再出现分片或有效 `done`；
- 无语义模型时 Host + Sidecar 稳态 RSS 不超过 150 MiB，24 小时增长不超过 20 MiB 且不超过 10%；
- 配置、历史导出、数据库迁移和密钥轮换具备原子性或可验证恢复路径；
- 上游 Provider 故障被分类为可重试、需配置或不可恢复，不重复付费提交。

### 4.4 性能

- 不启用语义插件时，冷启动不导入 `torch`、`sentence-transformers` 或模型下载组件；
- 标准发布机型冷启动 P95 不超过 3 秒；
- 热 Sidecar 接收请求到首个本地状态事件 P95 不超过 200 ms；
- 流式渲染前后端均采用有界缓冲，不按字符制造无界事件积压；
- 历史列表分页和批处理在上限输入下保持可取消、可恢复；
- 性能指标分别标注“本地可控耗时”和“上游 Provider 耗时”。

### 4.5 可观测性与支持

- 每次请求有稳定诊断 ID，但不记录请求正文和响应正文；
- 本地诊断只记录协议版本、组件版本、阶段、Provider ID、模型 ID、错误分类、首包时间和总耗时；
- 诊断日志轮转且总量有上限，默认本地保存，不自动上传；
- 用户可导出脱敏诊断包，导出前执行二次敏感信息扫描；
- 崩溃、Sidecar 重启、配置恢复和历史恢复均有可查询事件。

### 4.6 发布与恢复

- 一个命令可以完成后端全量验证并返回可靠退出码；
- CI 在干净 Windows 环境执行 Python、Rust、前端领域契约、依赖审计和构建检查；
- 版本号在 Python 包、Tauri、安装包、Git 标签和发布说明中一致；
- 安装、覆盖安装、启动、关闭到托盘、卸载和残留检查有证据；
- 正式推广前完成 Windows 代码签名方案，避免未签名安装包直接面向普通用户；
- 每个发布版本提供回滚包、配置兼容说明和数据恢复说明。

## 阶段 1：Provider 与 Runtime 生产可靠性

目标版本：`v0.6.0-beta.13`  
目的：先建立取消、并发、输出和请求生命周期边界，再消除目录漂移并验证真实调用链。

主要任务：

- 修复 `OperationCancelled` 分类，取消不得转换成 Provider 错误；
- Provider 取消必须主动中断阻塞 HTTP 读取，而不是等待下一分片或网络超时；
- Runtime 建立活动任务和等待队列上限，超载不再创建新线程；
- Core 建立输出字节、分片数量和总执行时间上限；
- 请求 ID 改为会话级不可重放协议和有界生命周期，不允许达到固定上限后永久拒绝服务；
- 由 Runtime 暴露可信 Provider/模型目录和配置状态；
- Tauri Host 提供只读公开命令，前端只消费目录，不自行维护真值；
- 冻结 Provider 错误分类、重试条件、超时和取消语义；
- 增加 SSE 断帧、重复事件、超大响应、空响应和连接中断测试；
- 抽取稳定 Provider 传输契约，移除 OpenAI-compatible 对 MiniMax 私有实现的直接依赖；
- 增加 Sidecar 崩溃、重启、并发配置和请求隔离测试；
- 建立脱敏真实 Provider 冒烟工具，只记录类别和时延；
- 使用新生成且仅存系统安全存储的凭据完成一次流式和一次取消实机验证。

阶段门禁：

- Provider/模型目录只有一个可信来源；
- Mock、协议夹具和真实 MiniMax 冒烟均通过；
- 取消后不产生有效完成事件；
- 不发生自动跨 Provider 降级或重复付费请求；
- 冒烟记录不含密钥、输入和输出正文。
- 并发超限返回可理解忙碌错误，不增加线程；
- 输出和超时越界稳定终止且不返回半截成功结果。

`v1.0` Provider 政策：默认只正式宣传完成在线门禁的 Provider。MiniMax 作为首个正式 Provider；DeepSeek、Qwen、智谱和 SiliconFlow 在完成真实成功、取消、认证、限流、超时和断流验证前标为实验性或不展示。

`v1.0` 语义模型政策：默认安装包不携带重型语义运行依赖。运行组件缺失时入口必须明确禁用或隐藏，不得宣传为开箱即用；后续以可选组件形式单独验证。

## 7. 并发执行模型

每一阶段按四条并行轨道拆分：

1. 安全与数据；
2. Provider 与 Runtime 可靠性；
3. 性能、资源与可观测性；
4. 测试、CI、构建与发布。

并发规则：

- 子智能体必须拥有互不冲突的文件范围；
- 协议、配置 schema 和公共接口由主智能体统一决策；
- 子智能体不得读取或输出真实密钥，不得修改未分配文件；
- 每个子任务必须包含测试或可验证证据；
- 主智能体负责代码审查、冲突整合、全量复验、任务账本、提交和阶段总结；
- 阶段完成只代表进入下一阶段，不代表长期目标完成。

## 8. 提交与版本策略

- 每个提交只包含一个职责和一个验证闭环；
- 提交格式：`类型: 简要描述 | 版本号 | YYYY-MM-DD HH:MM`；
- 先提交验证基础设施，再提交行为变化，再提交发布文档；
- 每个阶段使用独立 beta/RC 标签；
- 只有阶段门禁全部通过后才推送标签；
- 发布阻塞问题不得通过修改文档状态绕过。

## 9. 停止条件

只有出现以下情况才暂停并请求用户决策：

- 需要使用、迁移或轮换真实密钥；
- 需要购买代码签名证书、部署服务或发生外部费用；
- 需要不可逆删除用户历史、配置、模型或发布产物；
- 需要改变隐私策略、遥测策略或 Provider 商业策略；
- 连续两轮验证失败且存在互斥技术取舍；
- 项目规则与生产目标发生冲突。

除此之外，按任务账本持续推进，不因单个阶段或单份报告完成而停止。

## 10. 工程评审结论

推荐：`go`，但按以下顺序实施：

1. 先解除生产开发模式、无界并发、无界输出和错误取消分类四项阻塞；
2. 再建立统一验证、CI、版本和供应链门禁；
3. 然后冻结 Provider 传输契约和动态目录；
4. 最后进入真实 Provider、安全数据、性能浸泡和安装发布阶段。

架构边界：资源限制和取消语义属于 Core/Runtime/Provider；窗口导航和发布完整性属于 Rust Host；前端只负责呈现和受控外链动作。

最高风险：在未完成资源治理和生产模式隔离前直接扩大公开测试，会把开发语义和资源耗尽风险带给用户。

最小修正：阶段 0 先完成 Release/Mock 隔离；阶段 1 首批完成取消、并发和输出边界，然后才接动态 Provider 目录。
