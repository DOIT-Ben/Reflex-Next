# 后端历史性能与保留策略验证

更新时间：2026-07-14

## 1. 结论

P3-008 的标准 10,000 条加密历史门禁通过。History SQLite 已具备有界保留、一次性索引迁移、5 秒关键词搜索硬截止、可取消全文扫描、恢复后保留元数据修复，以及可重复执行的性能基准。

## 2. 验证环境

- 系统：Windows 11 专业版，Build 26200
- CPU：Intel Core i5-1135G7，4 核 8 线程
- 内存：15.8 GiB
- Python：3.12.13
- uv：0.11.13
- 基线提交：`9bd8d2f`
- 数据集：10,000 条；每条 1 KiB 输入、4 KiB 输出；AES-GCM 加密

## 3. 生产预算

| 指标 | 门槛 |
|---|---:|
| 保存 P95 / P99 | 30 ms / 100 ms |
| 分页 P95 / P99 | 50 ms / 150 ms |
| 关键词命中 / 未命中 | 2,000 ms；硬截止 5,000 ms |
| 导出首块 / 总耗时 | 500 ms / 10,000 ms |
| 密钥轮换 | 30,000 ms；硬上限 60,000 ms |
| 常态 / 轮换峰值磁盘 | 数据库 2 倍 / 3 倍 |

## 4. 正式结果

命令：

```powershell
uv run --frozen --project plugins\history-sqlite --extra dev python tools\benchmark_history_sqlite.py --record-count 10000 --profile small --storage-sample-every 100 --json-output workbench\history-benchmark-small-v2.json
```

| 指标 | 结果 | 判定 |
|---|---:|---|
| 保存 P50 / P95 / P99 | 15.351 / 28.087 / 37.382 ms | 通过 |
| 100 条分页 P50 / P95 / P99 | 7.528 / 9.196 / 9.897 ms | 通过 |
| 关键词命中 / 未命中 | 1,225.626 / 1,178.525 ms | 通过 |
| 导出首块 / 总耗时 | 6.987 / 7,168.004 ms | 通过 |
| 密钥轮换 | 6,325.191 ms | 通过 |
| 加载后数据库 | 57,925,632 B | 通过 |
| 轮换总峰值 | 115,908,801 B，约数据库 2.00 倍 | 通过 |

首轮保存 P95 为 37.869 ms，超过 30 ms 门槛。根因是容量页统计在每次保存时执行；将容量检查收敛到配置周期或已有清理积压后，同一工作负载第二轮通过。数量限制仍在每次保存时即时执行。

## 5. 行为与测试证据

- History 插件：`158 passed`
- 基准工具契约：`38 passed`
- 统一门禁脚本契约：通过
- small 10 条 smoke：通过
- heavy 2 条 smoke：通过
- 搜索在每批查询、每条记录和两段正文解密之间检查取消与单调时钟预算；超时固定返回 `history_search_timeout`
- 默认保留上限：10,000 条、180 天、512 MiB，任一先到；单批最多清理 500 条
- 备份默认保留 3 个、最长 30 天；活动轮换检查点引用的备份受保护
- 恢复缺少新保留元数据的旧备份时，会在替换完成前重建记录计数和保留状态
- 普通保存命中 `index_layout_version` 后不重复删除或创建索引

## 6. Heavy 边界

heavy 配置为每条 16 KiB 输入和 64 KiB 输出。10,000 条原始正文约 800 MiB，会主动触发默认 512 MiB 保留上限，因此不把 heavy 10,000 条称为完整保留基准。本轮以 2 条真实 smoke 验证大正文保存、分页、搜索、导出和轮换链路；正式 10,000 条门禁使用标准 small 数据集。

## 7. 剩余风险

- Provider 和评分组合查询仍可能使用 SQLite 临时排序，但标准 10,000 条分页预算已通过；后续数据分布变化时继续观察查询计划。
- 单次最大耗时受 Windows 调度和存储抖动影响，因此发布门禁以 P95/P99 为主，同时保留 max 指标用于趋势比较。
- 本验证不替代 P3-002 的 72 小时长期浸泡，也不替代安装升级生命周期验证。
