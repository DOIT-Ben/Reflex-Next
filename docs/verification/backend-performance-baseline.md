# 历史基线：Reflex Next 后端性能（2026-07-14）

更新时间：2026-07-14
> 历史证据提示：本文记录旧工作树的性能基准，不代表当前工作树的完整发布门禁。
对应任务：P3-001

## 1. 结论与证据边界

`tools\benchmark_backend.py` 已建立无网络、无真实凭据的后端延迟基准入口，覆盖：

- 冷启动：创建 Python Runtime 进程到首个 `ping` 状态事件；
- Runtime 首状态：已预热 Runtime 接收优化命令到首个本地状态事件；
- Provider 首包：已预热 Runtime 接收优化命令到本地 Mock 的首个 `chunk`；
- 总耗时：已预热 Runtime 接收优化命令到最终 `metric`；
- 取消延迟：发送取消命令到收到 `cancelled` 状态事件。

工具结果不是正式 SLO 证据。它只测量源码环境中的本地可控链路，不包含 Tauri Host、发布版 Sidecar 封装、WebView 渲染、网络、真实 Provider 排队或模型生成耗时。正式发布门禁还必须按第 6 节采集发布候选版本的完整链路证据。

## 2. 安全与资源边界

- 工具只启用固定的本地开发 Mock，不读取 Credential Manager、`.env` 或 Provider 环境变量；
- 子进程环境使用显式白名单，不继承可能包含凭据的环境变量；
- JSON 和人类摘要只包含环境、样本量、百分位、失败数、阈值及结论；
- 不输出单次原始样本，不记录输入正文、输出正文、密钥、端点或异常详情；
- 样本数范围为 `1..100`，默认 `10`；
- 单次等待上限为 `30` 秒，默认 `5` 秒；
- 每个 Runtime 都会优先正常关闭，超时后终止，避免遗留 Sidecar 进程。

## 3. 运行方式

在仓库根目录执行：

```powershell
uv run --frozen --project .\packages\reflex-runtime --extra dev python .\tools\benchmark_backend.py --samples 10 --timeout-seconds 5
```

stdout 为完整 JSON，stderr 为人类可读摘要。需要同时归档 JSON 时使用：

```powershell
uv run --frozen --project .\packages\reflex-runtime --extra dev python .\tools\benchmark_backend.py --samples 100 --timeout-seconds 5 --json-output .\backend-benchmark.json
```

`backend-benchmark.json` 是本地证据文件，不应默认提交仓库。参数非法时退出码为 `2`；采集完成但失败样本不为零或任一 P95 超过阈值时退出码为 `1`；全部通过时为 `0`。

## 4. 统计和阈值

百分位使用 nearest-rank 算法。失败样本不进入百分位计算，但任意失败都会使对应指标结论为未通过。

| 指标 | P95 阈值 | 来源 | 说明 |
|---|---:|---|---|
| 冷启动 | 3000 ms | 生产 SLO | 与生产路线图一致 |
| Runtime 首状态 | 200 ms | 生产 SLO | 仅限已预热本地 Runtime |
| Provider 首包 | 500 ms | 本地夹具护栏 | 不代表真实 Provider SLO |
| 本地 Mock 总耗时 | 1000 ms | 本地夹具护栏 | 只用于发现本地链路回退 |
| 取消确认 | 250 ms | 生产 SLO | 本地取消确认预算 |

阈值结论来自 P95 和失败数；P50/P99 用于观察分布，不单独决定退出码。真实 Provider 的首包和总耗时必须拆分为本地可控耗时与上游耗时，不得用本地 Mock 结果替代。

## 6. 正式基线采集流程

正式基线必须满足以下流程，缺少任一项都只能标记为开发基线：

1. 冻结待测 RC 的提交哈希、统一版本号、安装包哈希和 Sidecar 哈希；不得使用有未提交后端改动的工作树作为正式证据。
2. 在最低支持配置、标准发布配置和一台较高配置机器上采集；记录 Windows 版本、补丁、CPU、逻辑处理器、内存、存储类型和电源模式。
3. 每台机器重启后等待系统空闲，关闭非必要前台任务，固定电源与网络条件；记录安全软件和系统更新状态，不通过临时关闭安全防护美化数据。
4. 先运行本工具 `100` 个样本，连续执行 `3` 轮。每轮保留独立 JSON，不合并或删除失败轮次。
5. 使用签名 RC 安装包从真实 Host 启动发布版 Sidecar，分别采集首次安装冷启动、后续冷启动、热首状态和本地取消确认；每项至少 `100` 个样本。
6. 通过设置页临时配置新凭据后，按真实 Provider 门禁流程单独采集首包和总耗时。只归档 Provider ID、模型 ID、错误分类和聚合耗时，不归档输入或输出正文；采集结束后按凭据管理流程清理测试凭据。
7. 校验每轮失败数为 `0`，正式 SLO 的 P95 达标，且 P99 不出现无法解释的长尾。任何失败、系统抢占或异常更新都必须保留原始证据并说明重跑原因。
8. 将 JSON、Host 侧聚合数据、机器清单、提交及产物哈希、运行命令和异常说明放入受控发布证据目录，并由另一位审查者复核。

本工具不会自动完成第 5、6 步。因此，P3-001 工具完成不等于阶段 3 性能门禁完成；还需要 P3-002/P3-003 的浸泡证据，以及发布候选版本的 Host 和真实 Provider 基线。
